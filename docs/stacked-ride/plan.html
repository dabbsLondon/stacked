// the idea

A virtual trainer.
Built for your stacked routes.

Stacked builds Frankenstein routes — climbs from across the country spliced into one ride. Stacked Ride is the companion that lets you actually ride them. Pull a route in, jump on the turbo, the trainer adjusts resistance to match the gradient under your virtual wheels, a low-poly bike + rider weaves through a 3D rendering of the course, and every watt, heartbeat, RPM and metre is recorded. At the end: a synthesised GPX/FIT you can post straight to Strava, plus a leaderboard against everyone else who's ridden the same stacked route.

// the loop

Telemetry in.
Position out. 60 times a second.

Three threads of the ride run continuously — a sensor loop pulling fresh power/HR/cadence values from BLE devices, a physics step turning power × gradient × CdA into a speed, and a renderer drawing the bike at its new position. A fourth thread records every sample to disk.

01 — SENSE

Pair the trainer, HRM, power meter

On first launch the app asks for permission to talk to BLE devices — one at a time. Smart trainer (FTMS), heart rate monitor (HRS), optional separate power meter (CPS), optional cadence sensor (CSC). Each connection persists for the session; values stream in at 1–4 Hz.

The trainer is both an input (power, cadence, speed) and an output (target grade). Send the current slope of the road and a calibrated trainer adjusts the wheel resistance so you feel the climb.

02 — PHYSICS

Power × gradient → speed

Standard cycling math, run at 60Hz. Forces opposing motion: rolling resistance + aero drag + gravity-on-slope. Forces propelling: rider power ÷ velocity. Net force × dt updates velocity; velocity × dt updates position along the route.

Position is one number — distance along the GPX. Convert distance to a 3D coordinate by interpolating the route's polyline. Look up the local gradient at the current position and write it back to the trainer once a second.

03 — RENDER

3D course, low-poly rider

Three.js scene reused from Stacked's 3D viewer. The route is a continuous ribbon — same geometry, just at ground level with proper texturing. A bike + rider glTF model sits on the path at the current position. Camera follows from behind-and-above; tilts with the gradient so the climbs look like climbs.

HUD overlay: current power, HR, cadence, speed, gradient %, distance, elapsed time, distance-to-summit. Configurable. Race-mode shows your ghost vs the leaderboard.

04 — RECORD

Save the ride. Export to Strava.

Every sample (~1 Hz) is appended to an in-memory buffer: timestamp, lat, lon, ele, dist, power, hr, cad, speed, gradient. On finish, encode as a FIT file using fit-encoder and offer download. If the user has linked Strava (OAuth2), one-click upload.

The ride summary saves to PocketBase: time, ascent, normalized power, average HR, segments. Feeds the leaderboard for that route + the rider's personal history.

// the relationship

Stacked builds routes.
Stacked Ride consumes them.

Two repos, one PocketBase, one user-facing app each. Stacked is the browser app — compose climbs anywhere with a Chromium tab. Stacked Ride is the desktop app — installed on the laptop next to the turbo, paired with the trainer, used for the actual ride. Both talk to the same backend, share the same user accounts, and pass GPX routes one way and recorded rides the other.

What Stacked Ride pulls from Stacked

The route is the input. Stacked Ride doesn't compose, edit, or cut — that's all done upstream.

  • routes (read)A project's stitched GPX (climbs + bridges) loaded over the existing PocketBase projects collection. The public/library filtering applies — riders can race any public route, only their own private ones.
  • climbs metadata (read)Per-climb names, distances, gradients — straight from snapshot.stitch.climbs. Used to label the HUD ("Climbing: Hardknott · 2.1km · 14.3%") and to time segments for the leaderboard.
  • auth (shared)Same PB users, same magic role flag. Sign-in carries across both apps. An admin in Stacked is an admin in Ride.

What Stacked Ride writes back

The output is a permanent record of every ride, attributable to a route.

  • rides (write)New PB collection. One row per completed ride. Columns: route_id, rider_id, summary (time, ascent, NP, avg HR), samples (compressed second-by-second telemetry), fit_blob (optional, stored in PB Storage).
  • segment times (derived)Per-climb times sliced out of the ride samples. Powers the leaderboard.
  • strava (out)Optional. If a user has connected Strava, a successful ride POSTs the FIT to /api/v3/uploads.

Same skeleton as Stacked.
3D + BLE on top.

Almost all the foundation is reuse: React + Vite + TypeScript, PocketBase backend, Three.js. The new pieces are device IO (Web Bluetooth), a physics step, a FIT encoder, and a Strava OAuth flow.

// hardware compatibility

Both protocols supported.
Same app, same code.

Going thick-client means we're not constrained by Web Bluetooth. The Electron main process opens raw BLE GATT via noble and a USB ANT+ dongle via ant-plus-next. Both run in parallel — the app shows one unified list of available devices regardless of protocol.

// risks & open questions

What could go wrong.

Honest list. Most of these have workarounds; some shape the architecture from day one.

Likely real problems

  • BLE flakinessDevice reconnection after a dropout needs explicit handling. Different trainer firmwares respond differently to identical FTMS commands. Native libraries handle this better than Web Bluetooth, but it's still per-device tuning.
  • Native module buildsnoble + ant-plus depend on platform-native bindings. The CI build matrix needs Win/Mac/Linux runners and electron-rebuild needs to work on each.
  • Strava rate limits100 uploads / 15 min per app. Personal use is fine. If we ever go public, switch to per-user OAuth quotas.
  • FIT encoding gotchasStrava ingests FIT but is picky about lap markers and developer fields. First implementation will probably need 2-3 iterations to match what Garmin / Wahoo write.
  • Code signingMac requires Apple Developer ID (£99/yr) for users not to see "unidentified developer" warnings. Windows SmartScreen needs an EV cert (£200+/yr) to skip "this app is unsafe" prompts. Mitigate via clear install instructions; budget for it if going public.

Unknowns to spike before deciding

  • Your trainer modelStep-00 spike confirms it speaks FTMS over BLE (or FE-C over ANT+). Either works with our stack; we just need to know which path to wire first.
  • Power-to-speed calibrationReal-world cyclists with the same power on the same gradient ride at slightly different speeds. Pick a sensible default (75 kg rider, CdA 0.32, Crr 0.005) and let advanced users tweak.
  • Camera tilt vs world tiltTilting the camera looks more "Zwift" but can make people feel motion sick. Tilting the world is unusual but cleaner. Prototype both.
  • FIT vs TCX vs GPXStrava accepts all three; FIT is richest. Start with FIT but keep TCX as fallback.
